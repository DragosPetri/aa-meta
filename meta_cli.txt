Analog Attachable:
```
An Analog Attachable is any invocable binary that conforms to the attach-meta protocol.

Registration requires a single fixed command:
  <binary> attach-manifest  =>  writes manifest to disk, prints path to stdout

A fully conformant Analog Attachable implements the feedback loop:

  Required commands:
    - tool-config-get, tool-config-set
    - create-workfile
    - list-devices
    - add, read, update, delete
    - validate

  Optional commands (convenience):
    - move, rename, alias

  Optional commands (build pipeline):
    - generate, build, deploy

  Optional commands (intelligence):
    - list-intelligence, suggest

NOTE: a binary that supports only attach-manifest is registerable but not fully conformant
NOTE: the build pipeline is optional because for some tools workfile === artifact
NOTE: intelligence support is declared via list-intelligence presence in the manifest
```

───────────────────────────────────────────────────────────────────
Manifest
───────────────────────────────────────────────────────────────────

NOTE: manifest is a file whose path is emitted by the sub-tool during init
NOTE: argv includes the binary — different commands can route to different sub-tools
NOTE: list-intelligence presence in commands declares intelligence support
NOTE: absence of a command entry means unsupported
NOTE: tool extensions are purely additive — tool authors may only declare optional fields;
      required fields are owned by the protocol (enforced by meta-schema, see below)
NOTE: on every invocation, attach-meta reads the manifest from disk and merges the tool's
      args with the protocol base schema using allOf before validating input

Versioning:
  protocol_version follows semver (MAJOR.MINOR.PATCH)

  MAJOR — breaking changes: removed or renamed commands, changed required
           response shapes, changed transport contract
  MINOR — backwards-compatible additions: new optional commands, new
           optional fields on existing response types
  PATCH — no behavioral change: clarifications, corrections

  Mismatch handling (checked at init time):
    major mismatch  => hard error; attach-meta refuses to proceed
    minor mismatch  => allowed; attach-meta ignores unknown fields from a
                       newer tool, a newer attach-meta degrades gracefully
                       against an older tool
    patch mismatch  => always compatible; no action

// attach-meta ships a JSON Schema validator and validates every incoming manifest
// against this meta-schema at init time.
```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "attach-meta/manifest",
  "type": "object",
  "required": ["protocol_version", "commands"],
  "additionalProperties": false,
  "properties": {
    "protocol_version": {
      "type": "string",
      "pattern": "^\\d+\\.\\d+\\.\\d+$"
    },
    "commands": {
      "type": "object",
      "propertyNames": {
        "enum": [
          "read", "add", "delete", "move", "update", "rename", "alias",
          "validate", "generate", "build", "deploy",
          "list-devices", "create-workfile",
          "tool-config-get", "tool-config-set",
          "list-intelligence", "suggest"
        ]
      },
      "additionalProperties": { "$ref": "#/$defs/CommandMapping" },
      "required": [
        "tool-config-get", "tool-config-set",
        "create-workfile", "list-devices",
        "add", "read", "update", "delete",
        "validate"
      ]
    }
  },
  "$defs": {
    "CommandMapping": {
      "type": "object",
      "required": ["argv"],
      "additionalProperties": false,
      "properties": {
        "argv": {
          "type": "array",
          "items": { "type": "string" },
          "minItems": 1
        },
        "args": {
          "$ref": "https://json-schema.org/draft/2020-12/schema"
        },
        "completions": {
          "type": "array",
          "items": {
            "type": "object",
            "required": ["arg", "kind"],
            "additionalProperties": false,
            "properties": {
              "arg":  { "type": "string" },
              "kind": { "type": "string" }
            }
          }
        }
      }
    }
  }
}
```

// The protocol owns a base schema per command (hardcoded in attach-meta).
// At dispatch time, attach-meta merges base + tool args:
//   effective_schema = { "allOf": [base, manifest["commands"][cmd]["args"]] }
// Input is validated against the effective schema before forwarding to the subtool.
// Tool args may only add optional properties — a top-level "required" keyword is
// forbidden and attach-meta will reject a manifest that declares one, so the
// protocol always controls what is required.
//
// In completions entries, arg has two roles:
//   - a flag name (without "--") => completes the value of that flag
//   - the subcommand name        => completes positional args for the command
// The __complete dispatch rule distinguishes them by whether the preceding word
// starts with "--". A flag name must not equal its command's own name.

// Example — tool manifest entry for add:
```json
"add": {
  "argv": ["attach-pickle", "add"],
  "args": {
    "properties": {
      "bus_id": { "type": "string" }
    }
  },
  "completions": [
    { "arg": "add",    "kind": "device-key" },
    { "arg": "parent", "kind": "node-key"   },
    { "arg": "bus_id", "kind": "bus-id"     }
  ]
}
```

// Example — protocol base schema for add (lives in attach-meta, not in the manifest):
```json
{
  "properties": {
    "key":    { "type": "string" },
    "name":   { "type": "string" },
    "parent": { "type": "string" }
  },
  "anyOf": [
    { "required": ["key"] },
    { "required": ["name"] }
  ]
}
```

───────────────────────────────────────────────────────────────────
Transport Contract
───────────────────────────────────────────────────────────────────

Every command invocation is a subprocess call. The contract between
attach-meta and a sub-tool:

  Exit 0    stdout contains valid JSON matching the command's response type
            stderr may contain informational text (ignored by attach-meta)

  Non-zero  the operation could not complete; stdout is undefined
            stderr should contain a human-readable reason

NOTE: attach-meta treats non-zero exit, empty stdout, and malformed JSON
      as transport errors and surfaces them in its own error envelope —
      sub-tools are not responsible for these cases
NOTE: ok: false in a CommonResponse always corresponds to exit 0 — the
      tool ran and produced a valid response, but the operation failed;
      transport failures and protocol failures are distinct

───────────────────────────────────────────────────────────────────
Shared Types
───────────────────────────────────────────────────────────────────

CommonResponse = {
  ok:       true | false,
  message:  string,
  severity: "info" | "warn" | "error",
}

NOTE: ok is the only semantic gate — false means the operation failed
NOTE: severity is a display hint for message, not a second error signal
NOTE: ok: true  + severity: "warn"  => success with caveats
NOTE: ok: false + severity: "error" => canonical failure shape

Number: {
  kind: "number",
  subtype: "int" | "float",
}

String: {
  kind: "string"
}

Bool: {
  kind: "bool"
}

Enum: {
  kind: "enum",
  options: { value: string | number, display_string?: string }[]
}

// Variable-length, all items same type
Array: {
  kind: "array",
  items: TYPES
}

// Fixed-length, each position independently typed
Tuple: {
  kind: "tuple",
  items: TYPES[]
}

TYPES = Number | String | Bool | Enum | Array | Tuple;
// NOTE: TYPES is exclusively used by the read command (Node properties)

Property: {
  key: string,
  type: TYPES,
  value: string | number | bool | (string | number | bool)[]
}

NOTE: value is a JSON-serialisable value whose concrete shape matches the declared type

Node: {
  key: string,
  properties: Property[],
  children: Node[],
  alias?: string[]
}

NOTE: alias is absent when the active tool does not declare alias support in its manifest

ValidIdentifier: string
// any non-empty string; a node name within its parent scope, or an alias
// character grammar is not constrained by the protocol — sub-tools define what is valid

NOTE: a sequence of ValidIdentifiers forms a path resolved left-to-right from root
NOTE: a path may terminate at any Node or at a property of any Node
NOTE: aliases are only valid as identifiers if the underlying format enforces their uniqueness
NOTE: it is the sub-tool's responsibility to accept this way of addressing nodes/properties irrespective of underlying format

───────────────────────────────────────────────────────────────────
Commands — Initialization
───────────────────────────────────────────────────────────────────

COMMAND:
```
attach-meta init <analog_attachable> [--no-interactive] => CommonResponse | InitResponse

  1. calls <analog_attachable> attach-manifest
  2. sub-tool writes manifest to disk, outputs path to stdout
  3. attach-meta reads manifest from that path
  4. validates manifest against the protocol meta-schema
  5. checks protocol_version major matches attach-meta's major; fails on mismatch
  6. if all valid => writes binary + manifest path to .attach-meta.toml
  7. (default) runs interactive config session:
       a. requests all configs via tool-config-get
       b. loops through required fields asking for input
          (if default exists, asks if default shall be used)
       c. displays optional fields, asks if any shall be configured
       d. calls tool-config-set for each provided value

InitResponse = CommonResponse & {
  config_complete: true | false,
  missing_fields: string[],
}

NOTE: --no-interactive skips step 7 and returns InitResponse instead of CommonResponse
NOTE: 3rd parties use --no-interactive and drive their own config session via tool-config-get/tool-config-set
NOTE: the underlying TOOL is permitted to do any pre/post init operations
```

attach-meta add [[Device.key | name] | [Device.key && name]] [parent?] => CommonResponse

COMMAND:
```
attach-meta read [...ValidIdentifier] => Node | Property

NOTE: missing ValidIdentifier means implicit root (returns the full tree)
NOTE: reading a node always returns its full subtree

attach-meta read                                         => Node (root, full tree)
attach-meta read soc spi@7e400000 my_adc                => Node (subtree rooted at my_adc)
attach-meta read my_adc                                  => Node (subtree rooted at my_adc)
attach-meta read my_adc spi_max_freq                     => Property
attach-meta read soc spi@7e400000 ad7124@0 spi_max_freq  => Property
```

COMMAND:
```
attach-meta update [ValidIdentifier, ...ValidIdentifier] --with [value] => CommonResponse

NOTE: only properties can be updated
NOTE: update behaves like "upsert" if no property is found, it will be inserted
```

COMMAND:
```
DeletePreview = CommonResponse & {
  node_count:     number,
  property_count: number,
}

attach-meta delete [...ValidIdentifier] [--force] => CommonResponse | DeletePreview

NOTE: leaf nodes and properties are deleted directly without --force
NOTE: deleting a non-leaf node or implicit root without --force returns DeletePreview (no changes made)
NOTE: --force is required to execute a waterfall delete, including root
NOTE: delete means whatever the underlying TOOL considers

attach-meta delete                                           => DeletePreview (root, dry run)
attach-meta delete --force                                   => CommonResponse (delete all)
attach-meta delete soc spi@7e400000 my_adc                  => CommonResponse | DeletePreview
attach-meta delete my_adc spi_max_freq                      => CommonResponse (property)
attach-meta delete soc spi@7e400000 ad7124@0 spi_max_freq   => CommonResponse (property)
```

COMMAND:
```
attach-meta move [ValidIdentifier, ...ValidIdentifier] --to [...ValidIdentifier] => CommonResponse

NOTE: only nodes are movable
NOTE: no implicit root for positional (can't move root)
NOTE: no implicit root for --to
NOTE: each TOOL is allowed to have rules when moving so it's more convenient to have a dedicated COMMAND

Move workflow (fallback) when native move is unsupported:
  1. read node (returns full subtree)
  2. depth-first, add each node in the subtree under its new parent:
     - the root node is added under the target parent by Device.key or name
     - each child is added under its corresponding newly-created parent
  3. for each added node, update all its properties with values read in step 1
  4. delete old node with --force
```

COMMAND:
```
attach-meta rename [ValidIdentifier, ...ValidIdentifier] [value] => CommonResponse

NOTE: shall work for nodes and for properties as there are valid use-cases for renaming a property (e.g. aliases in devicetree)

Rename workflow (fallback) when not natively supported by the underlying tool:

  For a node:
    1. read node (returns full subtree)
    2. add a new node with the new name under the same parent
    3. depth-first, re-create all descendants under the new node:
       add each by Device.key or name under its corresponding new parent
    4. for each added node, update all its properties with values read in step 1
    5. delete old node with --force

  For a property:
    1. read property value
    2. update (upsert) new property key with that value
    3. delete old property key
```

COMMAND:
```
attach-meta alias [...ValidIdentifier] --with <value>   => CommonResponse
attach-meta alias [...ValidIdentifier] --remove <value> => CommonResponse

NOTE: --with and --remove are mutually exclusive
NOTE: path identifies the target node; aliases are not valid on properties
NOTE: presence of alias in the manifest declares support — not all formats support aliases
```

Error = {

  path:    ValidIdentifier[],   // empty array means file-level error

  errors:   Error[],
  warnings: Error[],

───────────────────────────────────────────────────────────────────
Commands — Completions
───────────────────────────────────────────────────────────────────

COMMAND:
```
attach-meta completion ["bash" | "zsh" | "fish"]

NOTE: will output completion script for attach-meta to stdout
NOTE: help will contain useful information for a user what to do with the completion script for each supported shell
```

Autocompletion hook system:

On <TAB>: attach-meta __complete -- <subcommand> [args...] <partial>

NOTE: global flags are stripped from args before processing
NOTE: <partial> is the word currently being completed (may be empty)
NOTE: a completions entry arg must not equal the subcommand name; tool authors must avoid this collision

attach-meta side:
  1. If <subcommand> is absent: complete from known command list; done
  2. If <subcommand> is "suggest":
     a. If completing the first positional (kind): call list-intelligence; output Intelligence[].kind one per line; done
     b. If completing the Nth subsequent positional:
        - look up the Intelligence entry for the specified kind
        - get IntelligenceArg[N] (0-indexed after kind)
        - if the arg has a kind field and it is advertised by list-intelligence:
          call suggest <IntelligenceArg.kind> [...preceding positional args]; output Suggestion[].value one per line
        - otherwise: output nothing
        done
  3. Inspect the word immediately preceding <partial>:
     a. If it starts with "--": strip "--" → flag_name; look up completions[arg == flag_name]
     b. Otherwise: look up completions[arg == subcommand]
  4. If a completions entry exists: check the kind is advertised by list-intelligence
  5. If advertised: call attach-meta suggest <kind> [...preceding positional args]; output Suggestion[].value one per line
  6. If not advertised or no completions entry: output nothing
  7. Exit 0 (non-zero/empty stdout => no candidates)

NOTE: __complete is a shell adapter over suggest — tools implement suggest only
NOTE: an unadvertised kind in completions silently yields no candidates; it is not an error
NOTE: agents call suggest directly for structured Suggestion[] output;
      shells call __complete for line-per-value output — same code path
NOTE: for positional completion, all preceding positional args are forwarded as context
      to suggest — the subtool can dynamically vary suggestions based on prior tokens
