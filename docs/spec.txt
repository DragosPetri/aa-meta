Analog Attachable:
```
An Analog Attachable is any invocable binary that conforms to the attach-meta protocol.

Registration requires a single fixed command:
  <binary> attach-manifest  =>  writes manifest to disk, prints path to stdout

A fully conformant Analog Attachable implements the feedback loop:

  Required commands:
    - tool-config-get, tool-config-set
    - create-workfile
    - list-devices
    - add, read, update, delete
    - validate

  Optional commands (convenience):
    - move, rename, alias

  Optional commands (build pipeline):
    - generate, build, deploy

  Optional commands (intelligence):
    - list-intelligence, suggest

NOTE: a binary that supports only attach-manifest is registerable but not fully conformant
NOTE: the build pipeline is optional because for some tools workfile === artifact
NOTE: intelligence support is declared via list-intelligence presence in the manifest
```

───────────────────────────────────────────────────────────────────
Manifest
───────────────────────────────────────────────────────────────────

NOTE: manifest is a file whose path is emitted by the sub-tool during init
NOTE: argv includes the binary — different commands can route to different sub-tools
NOTE: list-intelligence presence in commands declares intelligence support
NOTE: absence of a command entry means unsupported
NOTE: tool extensions are purely additive — tool authors may only declare optional fields;
      required fields are owned by the protocol (enforced by meta-schema, see below)
NOTE: every command that routes to a subtool shall re-read the manifest from the path
      stored in .attach-meta.toml; the SHA-256 of the file contents is compared against the
      value stored alongside the path:
        hash unchanged  => parse only, skip validation
        hash changed    => full meta-schema + version validation; on success,
                           update stored hash in .attach-meta.toml; on failure,
                           hard error (stored hash not updated, so next
                           invocation re-validates)
        file missing or unreadable => hard error
NOTE: after reading the manifest, attach-meta merges the tool's args with the protocol
      base schema using allOf before validating input

Versioning:
  protocol_version follows semver (MAJOR.MINOR.PATCH)

  MAJOR — breaking changes: removed or renamed commands, changed required
           response shapes, changed transport contract
  MINOR — backwards-compatible additions: new optional commands, new
           optional fields on existing response types
  PATCH — no behavioral change: clarifications, corrections

  Mismatch handling (checked at init time):
    major mismatch  => hard error; attach-meta refuses to proceed
    minor mismatch  => allowed; attach-meta ignores unknown fields from a
                       newer tool, a newer attach-meta degrades gracefully
                       against an older tool
    patch mismatch  => always compatible; no action

  NOTE: version is checked at init time and re-checked whenever the manifest
        file's content hash changes (see manifest re-read rules above). A tool
        update that changes protocol_version but does not cause the manifest
        file to be rewritten will not be detected — re-running init is required
        after any tool update that changes protocol_version.
  TODO: consider a mechanism to detect tool binary updates independently of
        manifest content changes so that a stale major version cannot go unnoticed

// attach-meta ships a JSON Schema validator and validates every incoming manifest
// against this meta-schema at init time.
// See: docs/schemas/manifest.schema.json

// The protocol owns a base schema per command (hardcoded in attach-meta).
// At dispatch time, attach-meta merges base + tool args:
//   effective_schema = { "allOf": [base, manifest["commands"][cmd]["args"]] }
// Input is validated against the effective schema before forwarding to the subtool.
// Tool args may only add optional properties — a top-level "required" keyword is
// forbidden and attach-meta will reject a manifest that declares one, so the
// protocol always controls what is required.
//
// Flag parsing rules (applies to all commands):
//   - boolean flag  ("type": "boolean") — takes no value; presence sets it true
//   - string flag   ("type": "string")  — consumes exactly the next token as its value
//   - array flag    ("type": "array")   — consumes ALL following tokens until the next
//                                         "--"-prefixed token (or end of args); requires
//                                         at least one value; forwarded to the subtool
//                                         as --flag val1 val2 ... (flag name once, all
//                                         values as separate positional tokens after it)
//   - unknown flag  — treated as a string flag (forward as-is)
//
// In completions entries, arg has two roles:
//   - a flag name (without "--") => completes the value of that flag
//   - the subcommand name        => completes positional args for the command
// The __complete dispatch rule distinguishes them by whether the preceding word
// starts with "--". A flag name must not equal its command's own name.

// Example — tool manifest entry for add:
```json
"add": {
  "argv": ["attach-pickle", "add"],
  "args": {
    "properties": {
      "bus_id": { "type": "string" }
    }
  },
  "completions": [
    { "arg": "add",    "kind": "device-key" },
    { "arg": "to",     "kind": "node-key"   },
    { "arg": "bus_id", "kind": "bus-id"     }
  ]
}
```

// Example — protocol base schema for add (lives in attach-meta, not in the manifest):
```json
{
  "properties": {
    "key":  { "type": "string", "x-positional": true },
    "name": { "type": "string" },
    "to":   { "type": "array", "items": { "type": "string" } }
  },
  "anyOf": [
    { "required": ["key"] },
    { "required": ["name"] }
  ]
}
```

───────────────────────────────────────────────────────────────────
Transport Contract
───────────────────────────────────────────────────────────────────

Every command invocation is a subprocess call. The contract between
attach-meta and a sub-tool:

  Exit 0    stdout contains valid JSON matching the command's response type
            stderr may contain informational text (ignored by attach-meta)

  Non-zero  the operation could not complete; stdout is undefined
            stderr should contain a human-readable reason

NOTE: attach-meta treats non-zero exit, empty stdout, malformed JSON, and timeout
      as transport errors and surfaces them in its own error envelope —
      sub-tools are not responsible for these cases
NOTE: timeout_ms in CommandMapping is the subtool's declared ceiling for that command;
      if the process does not exit within timeout_ms, attach-meta kills it and raises
      a transport error; absence of timeout_ms means no timeout is enforced
NOTE: ok: false in a CommonResponse always corresponds to exit 0 — the
      tool ran and produced a valid response, but the operation failed;
      transport failures and protocol failures are distinct

Shared Types
───────────────────────────────────────────────────────────────────

// See: docs/schemas/responses.schema.json
// Defines: CommonResponse, TYPES (Number, String, Bool, Enum, Array, Tuple),
//          PropertyValue, Property, Node, ValidIdentifier

NOTE: ok is the only semantic gate — false means the operation failed
NOTE: severity is a display hint for message, not a second error signal
NOTE: ok: true  + severity: "warn"  => success with caveats
NOTE: ok: false + severity: "error" => canonical failure shape
NOTE: ok: true  + severity: "error" => protocol invariant violation; must never occur

NOTE: TYPES is exclusively used by the read command (Node properties)
NOTE: PropertyValue is recursive — nesting depth follows the structure declared by type
NOTE: alias is absent when the active tool does not declare alias support in its manifest

NOTE: a sequence of ValidIdentifiers forms a path resolved left-to-right from root
NOTE: a path may terminate at any Node or at a property of any Node
NOTE: aliases are only valid as identifiers if the underlying format enforces their uniqueness
NOTE: it is the sub-tool's responsibility to accept this way of addressing nodes/properties irrespective of underlying format

───────────────────────────────────────────────────────────────────
Commands — Initialization
───────────────────────────────────────────────────────────────────

COMMAND:
```
attach-meta init <analog_attachable> [--no-interactive] => InitResponse

  1. calls <analog_attachable> attach-manifest
  2. sub-tool writes manifest to disk, outputs path to stdout
  3. attach-meta reads manifest from that path
  4. validates manifest against the protocol meta-schema
  5. checks protocol_version major matches attach-meta's major; fails on mismatch
  6. if all valid => writes binary, manifest path, and manifest SHA-256 to .attach-meta.toml
  7. (default) runs interactive config session:
       a. requests all configs via tool-config-get
       b. loops through required fields asking for input
          (if default exists, asks if default shall be used)
       c. displays optional fields, asks if any shall be configured
       d. calls tool-config-set for each provided value

NOTE: missing_fields contains Config.field_name strings for all required configs
      that are either absent or set to an invalid value
NOTE: attach-manifest failure cases — all abort init with an error:
  - non-zero exit from the binary
  - empty stdout or stdout that is not a readable path
  - file at the path contains malformed JSON
  - JSON fails meta-schema validation (step 4)
  - protocol_version major mismatch (step 5)
NOTE: InitResponse is always returned regardless of --no-interactive
NOTE: --no-interactive skips step 7; config_complete and missing_fields reflect the state after init
NOTE: 3rd parties use --no-interactive and drive their own config session via tool-config-get/tool-config-set
NOTE: the underlying TOOL is permitted to do any pre/post init operations
```

Commands — Configuration
───────────────────────────────────────────────────────────────────

NOTE: every TOOL needs to provide a mechanism for reading/writing its config file

COMMAND:
```
attach-meta tool-config-get => gets all configs for the tool => ToolConfigResponse
attach-meta tool-config-get [field, ...field] => gets config of field(s) => ToolConfigResponse
attach-meta tool-config-set [field] [value] => set config field to value => CommonResponse

NOTE: Config.default is the schema-declared fallback; null means no default exists;
      null is not a valid default value — configs are always paths, strings, numbers,
      or enums
NOTE: Config.value is the currently stored value; null means not yet set
NOTE: sub-tools must pre-populate required configs that have a declared default into
      their config store so Config.value reflects a usable value from first call
NOTE: tool-config-set overwrites Config.value; the default is always preserved and
      can be restored by setting the value back explicitly
NOTE: missing_fields in InitResponse lists required configs whose Config.value is null
```

Commands — CRUD
───────────────────────────────────────────────────────────────────

COMMAND:
```
attach-meta add [<Device.key>] [--name <name>] [--to ...ValidIdentifier] => AddResponse

NOTE: at least one of the positional key or --name must be present; both may be supplied together
NOTE: the positional arg is the device key; --name is an additional human-readable name
NOTE: --to is the parent path (array flag — see flag parsing rules); absent means root
NOTE: key in AddResponse is the device key of the created node (positional key if supplied, else tool-generated)
NOTE: path in AddResponse is the absolute path from root to the created node
```

COMMAND:
```
attach-meta read [...ValidIdentifier] => Node | Property

NOTE: missing ValidIdentifier means implicit root (returns the full tree)
NOTE: reading a node always returns its full subtree
NOTE: path is absolute from root — there is no implicit tree-search; a single identifier refers to a root-level node or property
NOTE: aliases may be used as path components if the tool declares alias support; path resolution, including alias resolution, is the subtool's responsibility

attach-meta read                                         => Node (root, full tree)
attach-meta read soc spi@7e400000 my_adc                => Node (subtree rooted at my_adc)
attach-meta read my_adc                                  => Node (subtree rooted at my_adc)
attach-meta read my_adc spi_max_freq                     => Property
attach-meta read soc spi@7e400000 ad7124@0 spi_max_freq  => Property
```

COMMAND:
```
attach-meta update [ValidIdentifier, ...ValidIdentifier] --with <value> => CommonResponse

NOTE: only properties can be updated
NOTE: update behaves like "upsert" — if the property is not found, it is inserted
      under the resolved parent node; all nodes in the path must already exist
NOTE: --with takes a raw string forwarded as-is to the subtool; the subtool is responsible for parsing and type coercion
```

COMMAND:
```
attach-meta delete [...ValidIdentifier] [--force] => CommonResponse | DeletePreview

NOTE: leaf nodes and properties are deleted directly without --force
NOTE: deleting a non-leaf node or implicit root without --force returns DeletePreview (no changes made)
NOTE: --force is required to execute a waterfall delete, including root
NOTE: delete means whatever the underlying TOOL considers

attach-meta delete                                           => DeletePreview (root, dry run)
attach-meta delete --force                                   => CommonResponse (delete all)
attach-meta delete soc spi@7e400000 my_adc                  => CommonResponse | DeletePreview
attach-meta delete my_adc spi_max_freq                      => CommonResponse (property)
attach-meta delete soc spi@7e400000 ad7124@0 spi_max_freq   => CommonResponse (property)
```

COMMAND:
```
attach-meta move [ValidIdentifier, ...ValidIdentifier] --to [...ValidIdentifier] => CommonResponse

NOTE: only nodes are movable
NOTE: no implicit root for positional (can't move root)
NOTE: --to is the destination parent path (array flag — see flag parsing rules); no implicit root
NOTE: each TOOL is allowed to have rules when moving so it's more convenient to have a dedicated COMMAND

Move workflow (fallback) when native move is unsupported:
  1. read node (returns full subtree)
  2. depth-first, add each node in the subtree under its new parent:
     - the root node is added under the target parent by Device.key or name
     - each child is added under its corresponding newly-created parent
  3. for each added node, update all its properties with values read in step 1
  4. delete old node with --force

NOTE: the fallback is not atomic — a failure at any step leaves the workfile in its
      current partial state; attach-meta reports which step failed; callers are
      responsible for inspecting and recovering the workfile
```

COMMAND:
```
attach-meta rename [ValidIdentifier, ...ValidIdentifier] --to <value> => CommonResponse

NOTE: shall work for nodes and for properties as there are valid use-cases for renaming a property (e.g. aliases in devicetree)
NOTE: path identifies the target node or property; --to is the new name

Rename workflow (fallback) when not natively supported by the underlying tool:

  For a node:
    1. read node (returns full subtree)
    2. add a new node with the new name under the same parent
    3. depth-first, re-create all descendants under the new node:
       add each by Device.key or name under its corresponding new parent
    4. for each added node, update all its properties with values read in step 1
    5. delete old node with --force

  For a property:
    1. read property value
    2. update (upsert) new property key with that value
    3. delete old property key

NOTE: the fallback is not atomic — a failure at any step leaves the workfile in its
      current partial state; attach-meta reports which step failed; callers are
      responsible for inspecting and recovering the workfile
```

COMMAND:
```
attach-meta alias [...ValidIdentifier] --with <value>   => CommonResponse
attach-meta alias [...ValidIdentifier] --remove <value> => CommonResponse

NOTE: --with and --remove are mutually exclusive
NOTE: path identifies the target node; aliases are not valid on properties
NOTE: presence of alias in the manifest declares support — not all formats support aliases
```

COMMAND:
```
attach-meta validate [...ValidIdentifier] => ValidationResponse

NOTE: the sub-tool always validates the full workfile
NOTE: if a path is provided, attach-meta filters both errors and warnings

      filtering is attach-meta's responsibility, not the sub-tool's

      errors[] is self-describing (empty = valid); infra-level failures

      representation to the ValidIdentifier[] format
```

Meta Autocompletion — attach-meta __complete:

The shell hooks generated by `completion` call:

  attach-meta __complete -- <subcommand> [args...] <partial>

__complete always exits 0; empty stdout means no candidates.

NOTE: <partial> is the word currently being completed (may be empty string)
NOTE: global flags (--tool, --config, etc.) are consumed by Phase 1 arg parsing
      before __complete sees the remaining tokens — [args...] contains only
      protocol-level args
NOTE: tool authors implement suggest and list-intelligence only; completions
      entries in the manifest are metadata consumed solely by __complete —
      the tool never receives __complete calls

__complete algorithm (everything after "--" is passed in as args):
  1. If <subcommand> is absent or not a recognized command name:
     output each command name that starts with <subcommand> (empty = all); done
  2. If <subcommand> is "suggest":
     a. If the kind has not yet been committed (no tokens after "suggest", or
        only a partial word): call list-intelligence; output Intelligence[].kind
        filtered by prefix match against <partial>; done
     b. If completing an argument after the kind (Nth arg, 0-indexed after kind):
        - look up the Intelligence entry for the given kind
        - get IntelligenceArg[N]
        - if the arg has a kind field that is advertised by list-intelligence:
          call suggest <IntelligenceArg.kind> [...preceding positional args];
          output Suggestion[].value filtered by prefix; done
        - otherwise: output nothing; done
  3. Flag-name pass:
     If <partial> is empty or starts with "--", AND the word before <partial> is
     not a non-bool flag awaiting its value, AND either:
       - we are not inside an array flag's value run (see step 4b), OR
       - <partial> starts with "--" (user is explicitly requesting a flag), OR
       - we are inside an array flag's value run but that flag has no completions entry:
     output "--<flag>" for each flag from (base schema + tool args) that starts with
     <partial> (strip leading "--" first) and has not already appeared in [args...]
  4. Value-completion pass (runs after step 3 in the same invocation):
     a. If the word immediately preceding <partial> starts with "--":
        kind  = completions[arg == stripped-flag-name]
        context = [...preceding subcommand positionals]
     b. Otherwise, walk back past non-"--" tokens from <partial> to the nearest "--" flag:
        - Array flag found: kind    = completions[arg == array_flag_name]
                           context = [values already provided to that flag]
          (each flag treats its values like subcommand positionals — one completions entry,
           context grows as more values are added)
          If no completions entry for this flag: output flag names (step 3 fallback); done
        - No array flag (plain positionals): kind    = completions[arg == <subcommand>]
                                             context = [...preceding subcommand positionals]
     If kind is found and advertised by list-intelligence:
       call suggest <kind> [...context];
       output Suggestion[].value filtered by prefix
     Otherwise: output nothing

NOTE: "filtered by prefix" = only items where value.starts_with(<partial>) are emitted
NOTE: steps 3 and 4 both run in the same invocation; they are non-exclusive except when
      inside an array flag with a completions entry — there, step 3 is suppressed (unless
      <partial> starts with "--") so flag names and value suggestions don't mix
NOTE: an unadvertised kind in completions silently yields no candidates — not an error
NOTE: subcommand positional context excludes flag names and their values (string flags skip
      one token; array flags skip all following tokens until the next "--" flag)
NOTE: agents call suggest directly for structured Suggestion[]; shells call __complete
      for line-per-value output — same suggest call underneath

// In completions entries, arg serves three roles — step 4 selects by dispatch context:
//   - string/bool flag value  (step 4a — preceding word is "--flag"):
//       arg = flag name (without "--"); context = subcommand positionals
//   - array flag values       (step 4b — inside an array flag's value run):
//       arg = array flag name; context grows as each successive value is added
//   - subcommand positionals  (step 4b — no enclosing array flag):
//       arg = subcommand name; context grows as each successive positional is added
//
// Each command base schema declares at most one x-positional field. That field defines
// the positional slot for the command; its completion kind is declared with the SUBCOMMAND
// NAME as arg (not the field name). x-positional is a protocol concern — tool args may
// not declare it.
//
// Consequence: a flag-name entry must not use the subcommand name as its arg value —
// the two would be indistinguishable. Tool authors must avoid this collision.
